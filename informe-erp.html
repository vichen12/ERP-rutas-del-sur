Arquitectura General del Sistema

Como estan conectados todos los modulos y el principio fundamental de la caja

Principio Central: cajaService es el unico gateway financiero

Toda operacion que mueve dinero en el sistema debe pasar por cajaService. Ningun modulo escribe directamente en movimientos_caja. Esto garantiza consistencia, auditabilidad y balance correcto.

REGLA ABSOLUTA: Si una accion tiene impacto economico, usa cajaService. Nunca un INSERT INTO movimientos_caja directo desde un componente.

Tablas Nucleo del Sistema

viajes — Tabla de hechos principal. Cada viaje genera cascada en multiples tablas.
movimientos_caja — Libro mayor de todos los movimientos de dinero.
cuenta_corriente — Saldo de deuda de cada cliente con la empresa.
cuenta_corriente_choferes — Lo que la empresa le debe a cada chofer.
remitos — Puente entre viajes y facturas. Sin remito no hay factura.
facturas — Comprobantes fiscales emitidos ante AFIP/ARCA.

Ciclo de Vida Completo de una Operacion

1

Alta de Cliente y configuracion de tarifa

Se crea el cliente con su tarifa de flete, pago al chofer, litros estimados y km de ruta. Estos valores se auto-completan en cada viaje nuevo.

2

Creacion del Viaje (3 pasos)

Se seleccionan camion, chofer y clientes. El sistema calcula costos automaticamente. Se guarda en viajes + reparto_viaje.

3

Impacto automatico en Cuenta Corriente

Por cada cliente del viaje se genera una entrada en cuenta_corriente con debe = tarifa_flete. Estado: por_cobrar.

4

Cobro al cliente

Cuando el cliente paga, se registra via cajaService.registrarCobroFlete(). Entra como ingreso en movimientos_caja y se acredita en cuenta corriente.

5

Remito a Factura AFIP

El remito vincula el viaje con la factura. Se emite via ARCA y se guarda en facturas con CAE. El remito se marca facturado.

6

Pago al chofer

La liquidacion al chofer se hace via cajaService.registrarPagoChofer(). Sale de caja y se marca pagado en cuenta_corriente_choferes.

Viajes — El Nucleo Operativo

Como funciona el wizard de 3 pasos, que impacta en cada tabla y como se calculan los costos

Wizard de Creacion de Viaje (3 Pasos)

1

Paso 1 — Logistica Operativa

Se selecciona el camion y se auto-asigna el chofer. Luego se agregan clientes para IDA y opcionalmente VUELTA. Por cada cliente (reparto) el sistema auto-completa desde la ficha del cliente: tarifa de flete, pago al chofer, km de ruta, litros estimados, costo descarga, desgaste por km.

CLAVE: Si hay viaje de vuelta con clientes, el multiplicador de costos fijos = 2. Esto aplica a pago chofer y descarga (se recorre dos veces). Si es solo ida, multiplicador = 1.
2

Paso 2 — Analisis de Costos

Vista editable donde se puede ajustar el flete por cliente. El sistema calcula en tiempo real:

fleteBruto = SUM(monto_flete_ida) + SUM(monto_flete_vuelta) gasoil = lts_gasoil x precio_gasoil pagoChofer = pago_chofer x multiplicadorFijos descarga = costo_descarga x multiplicadorFijos desgaste = km_recorridos x desgaste_por_km totalCostos = gasoil + pagoChofer + descarga + desgaste neta = fleteBruto - totalCostos margen% = (neta / fleteBruto) x 100
3

Paso 3 — Manifiesto Final

Resumen completo con: desglose km ida/vuelta, utilidad/km, costo de gasoil, columnas: Flete Bruto | Gasoil | Chofer+Descarga | Fondo Desgaste. Se confirma y guarda.

Clientes — CRM y Cuenta Corriente

Como funciona el libro mayor por cliente, los saldos y el ciclo de cobro

Logica de Cuenta Corriente (Debe / Haber)

La cuenta corriente funciona como un libro contable por partida doble. Cada movimiento tiene debe (lo que el cliente nos debe) o haber (lo que el cliente pago).

DEBE -> El cliente nos debe dinero (aumenta saldo) HABER -> El cliente pago (reduce saldo) Saldo = SUM(debe) - SUM(haber) Si saldo > 0 -> Cliente nos debe Si saldo = 0 -> Esta al dia Si saldo < 0 -> Tenemos saldo a favor del cliente

Ejemplo de flujo tipico de un cliente

FechaTipo MovimientoDebeHaberSaldo Acum.
01/03Viaje REM-001 generado$20.000—$20.000
05/03Viaje REM-002 generado$25.000—$45.000
10/03Cobro parcial en caja—$15.000$30.000
20/03Cobro total restante—$30.000$0

estado_gestion — Ciclo del Cobro

por_cobrar
Viaje registrado, pago pendiente. El debe esta acreditado pero no cobrado.
maestro
Cobro recibido y confirmado. Factura emitida. Movimiento completo.
null
Movimiento manual (ajuste, nota de credito, etc.).

Destinos por Cliente

Cada cliente puede tener multiples destinos configurados con sus propias tarifas y distancias:

destinos_cliente { nombre, direccion, lat, lng, tarifa_flete, km_desde_base, lts_estimados, es_origen (bool), activo (bool) }

Al crear un viaje de reparto, seleccionar destino auto-completa km y litros.

Caja — Gateway Financiero Central

Como funciona cajaService, todas las categorias y la diferencia entre caja y banco

Caja vs Banco — La Separacion Fundamental

Todos los movimientos de dinero van a la misma tabla movimientos_caja, pero el campo tipo_cuenta los separa en dos flujos:

tipo_cuenta = 'caja' Efectivo fisico. Cobros al contado, pagos en mano, gastos operativos diarios. La caja chica del negocio.
tipo_cuenta = 'banco' Cuenta bancaria. Transferencias, tarjeta YPF, seguros, impuestos, leasing, prestamos. Todo lo electronico.
saldo_caja = SUM(ingresos) - SUM(egresos) WHERE tipo_cuenta='caja' saldo_banco = SUM(ingresos) - SUM(egresos) WHERE tipo_cuenta='banco' saldo_total = saldo_caja + saldo_banco

Banco — Cuenta Bancaria

Vista exclusiva de los movimientos electronicos y saldo bancario

Que aparece en Banco

El modulo banco filtra movimientos_caja donde tipo_cuenta = 'banco' y muestra:

Transferencias recibidas de clientes (ingresos)
Pagos YPF tarjeta (combustible_ypf)
Seguros (debito automatico)
Impuestos pagados electronicamente
Cuotas de leasing / prestamo
Transferencias entre caja y banco

Tipo de Cambio Dolar

La tabla configuracion guarda el tipo_cambio_dolar. El banco puede mostrar los saldos equivalentes en USD.

saldo_banco_ars = SUM(ingresos_banco) - SUM(egresos_banco) saldo_banco_usd = saldo_banco_ars / tipo_cambio_dolar
El tipo de cambio se actualiza manualmente desde la configuracion del sistema. No hay cotizacion automatica.

Nueva Carga

Costos Fijos, Impuestos y Multas

Estructura de costos fijos, punto de equilibrio y como se gestionan las multas

Estructura de Costos Fijos

La tabla costos_fijos almacena tanto costos operativos fijos como impuestos. La diferencia esta en el campo tipo:

Tipo = 'costo'

Alquiler de oficina, sueldos administrativos, servicios, leasing, etc. Montos fijos o semi-fijos.

Tipo = 'impuesto'

Ingresos Brutos, Sellos, Monotributo, etc. Pueden tener formulas dinamicas basadas en ventas.

Frecuencia de pago

FrecuenciaEquivalente mensualUso tipico
mensualmonto x 1Alquiler, servicios
trimestralmonto / 3Sellos, impuestos provinciales
semestralmonto / 6Seguros semestrales
anualmonto / 12Seguros anuales, patentes

Punto de Equilibrio (Break-Even)

La seccion PuntoEquilibrioSection calcula si la operacion del periodo cubre todos sus costos.

Variables disponibles en formulas

VENTAS -> SUM(tarifa_flete) del periodo GASOIL -> SUM(cargas_combustible.monto) CHOFERES -> SUM(cc_choferes.monto) VIAJES -> COUNT(viajes) NETO -> VENTAS - GASOIL - CHOFERES

Formula de equilibrio

costosFijos = SUM(costos_fijos.monto) prorateados al periodo ticketPromedio = VENTAS / VIAJES viajesNecesarios= costosFijos / ticketPromedio cobertura% = (VENTAS / costosFijos) x 100
Estado SALUDABLE: cobertura% mayor a 100%. Ingresos superan costos fijos. El excedente es la utilidad real del negocio.
Estado CRITICO: cobertura% menor a 100%. La operacion no cubre sus costos fijos. Se requieren mas viajes o reduccion de costos.

Multas

Las multas se registran en la tabla multas con su infractor (OBLIGATORIO), detalle, monto y estado.

Ciclo de vida de una multa

1

Alta de multa

Se registra: fecha, detalle, monto, infractor (nombre o patente), chofer_id o camion_id, estado='pendiente'.

2

Pago

Al marcar "Pagar", se llama a registrarPagoMulta(). Crea egreso en caja. estado='pagada'.

Facturacion ARCA / AFIP

Integracion completa con AFIP: autenticacion, firma digital, emision y guardado

Arquitectura de la Integracion AFIP

// Flujo de autenticacion y emision Frontend (FacturaWizard) | v POST /api/arca/facturar |-- /api/arca/auth | Lee cert + clave privada de configuracion DB | Firma TRA (Ticket de Requerimiento de Acceso) | Obtiene Token+Sign de WSAA (AFIP) | Cachea el token 12 horas en memoria del servidor | |-- WSFE (Web Service Facturacion Electronica) Envia: tipo_comprobante, punto_venta, cuit, importes Recibe: CAE + fecha_vencimiento_CAE

Wizard de 4 Pasos para Emitir Factura

1

Seleccionar Cliente y Datos Fiscales

Se selecciona el cliente. Se auto-completa CUIT y condicion IVA. Esto determina el tipo de comprobante a emitir.

2

Seleccionar Origen del Monto

Se puede vincular a un viaje (toma tarifa_flete), a un remito o ingresar monto manual.

3

Calculo de Impuestos

importe_neto = importe_total / (1 + alicuota/100) importe_iva = importe_total - importe_neto alicuota_iva = 21% (estandar) o 10.5% (reducida)
4

Emision ante AFIP

Se envia a /api/arca/facturar. AFIP responde con CAE. Se guarda en facturas y se actualiza remitos.facturado = true.

Tipos de Comprobante — Seleccion Automatica

Codigo DBTipoCuando se usa
1 Factura A Emisor RI + Receptor RI (Responsables Inscriptos). Discrimina IVA.

El tipo se determina combinando la condicion IVA del emisor (configuracion) con la del receptor (cliente). El wizard lo selecciona automaticamente.

Restricciones y Reglas Criticas del Sistema

1.
infractor es NOT NULL en multas.
Todo insert en multas DEBE incluir el campo infractor. Genera error 500 si se omite.
2.
gastos_camion NO tiene columna "tipo".
Solo tiene: camion_id, fecha, descripcion, monto, categoria. Incluir "tipo" genera error de columna.
3.
facturas.cae_vto es el nombre correcto (NO vencimiento_cae).
Usar vencimiento_cae en queries causa error de columna no encontrada.
4.
tipo_comprobante en facturas es TEXT ('1', '6', '11'), no entero.
Se guarda como string. El constraint fue eliminado para mayor flexibilidad.
5.
estado en facturas solo acepta: 'emitida', 'error', 'pendiente', 'manual'.
Cualquier otro valor viola el constraint facturas_estado_check.
6.
tarifa_flete_calculada no existe en la DB.
Es campo client-side. Siempre usar || Number(v.tarifa_flete) || 0 como fallback.
7.
destinos_cliente usa lat/lng (no latitud/longitud).
Filtrar activos con .eq('activo', true). Las coordenadas estan en lat y lng.
8.
cheques_diferidos: numero_cheque, banco y fecha_vencimiento son NOT NULL.
El formulario valida estos campos antes del INSERT y muestra toast descriptivo. Sin el script 3_cheques_setup.sql ejecutado, la tabla no tiene columnas tipo/destinatario/notas.
9.
Todos los movimientos de dinero DEBEN pasar por cajaService.
Nunca un INSERT directo en movimientos_caja desde componentes. Usar siempre las funciones del gateway.
